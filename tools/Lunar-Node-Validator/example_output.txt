=== 1. DEFINITION CHECK (before interpreting anything) ===
Swiss TRUE_NODE is an osculating node. Here it is rebuilt from Swiss' own Moon position+velocity with the same
cross-product formula the app uses, in 4 frame variants. The variant that matches Swiss TRUE_NODE shows which
definition Swiss uses; the app is then compared against that same definition as well.
quantity compared to Swiss TRUE_NODE longitude      RMS (arcsec)  max (arcsec)
  Swiss Moon vectors, apparent+nutation                      1.033         2.912
  Swiss Moon vectors, apparent, mean ecl.(NONUT)            12.884        19.037
  Swiss Moon vectors, true pos+nutation                      0.932         2.666
  Swiss Moon vectors, true pos, mean ecl.(NONUT)            12.874        18.701
  APP (Astronomy Engine Moon)                                   12.921        35.574
  APP vs best-matching Swiss-Moon variant                       13.030        35.522   (best = 'true pos+nutation')
  -> best variant matches Swiss TRUE_NODE to 0.932" RMS. Any larger app-vs-Swiss gap is ephemeris/numerics, not definition.

  1b. Amplification check. The osculating node is where the Moon's orbit plane cuts the ecliptic, so a small error
      in the Moon's latitude is magnified roughly 1/tan(5.145 deg) = 11.1 times in the node longitude.
      Moon latitude  app - Swiss(true pos): RMS 1.63"  max 5.64"
      Moon lat. rate app - Swiss          : RMS 0.46"/day  max 1.54"/day
      node longitude app - Swiss          : RMS 12.92"   (ratio node/lat = 7.9)
      -> A ~1-2" Moon latitude difference between the two Moon theories is enough to explain the node gap. This is
         consistent with 'ephemeris difference, amplified', not proof of which Moon theory is closer to the truth.

=== 4. NUMERICAL NOISE of the app's differences ===
  The node longitude uses an inner central difference of the Moon (d=0.02 d) and the speed an outer central
  difference of the node (h=0.005 d). Rounding noise e in longitude becomes speed noise ~ e/(h*sqrt2).
